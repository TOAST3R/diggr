## Context

Filtering a crate grew one capability at a time: the BPM range (`playlist-filters`) went into the footer, then style chips (`style-filter`), then ARTISTS/LABELS/FORMATS (`record-filters`), then the CART switch (`discogs-cart`). Each was squeezed between the footer buttons and the time readout's LCD box, and each fell back to a ☰ item when it didn't fit, so what a user sees depends on the playlist's width and the footer is crowded at every width. There is no text search.

What already works well, and stays: every filter feeds one predicate, `Shown` (`crates/ui/src/playlist.rs`), and everything downstream of it (list rows, next/previous/shuffle, the pre-warmed track, previews ahead, the title bar's `k/N`, P) reads `Shown` only. Those behaviours are tested through `pl_list()` and the play order, not through pixel positions.

Constraints found while exploring:
- The skin is a single bundled skin generated by `skin-gen` (`assets/skin/default/`, embedded with `include_bytes!`); there are no third-party skins to keep working, and a test checks the committed skin matches its generator.
- The playlist frame is built from stretchable bars (`pl_top_*`, `pl_bottom_*`) drawn by `draw_stretched_bar`; the footer's controls are painted at runtime in the LCD colour, not taken from the atlas.
- The skin font is upper case only, and `skin::fold` maps each character to one upper-case, accent-free character.
- `App::handle_keys` already returns early when `ctx.egui_wants_keyboard_input()`, so a focused egui `TextEdit` takes the letter keys away from the shortcuts.
- Headless tests compute list and footer positions as `PL_TOP + 20.0 + …` in 12 places (10 in `app.rs`, 2 in `record_tests.rs`).

## Goals / Non-Goals

**Goals:**
- One place for narrowing a crate, always visible, the same at every width (only denser or sparser).
- A live text search over the shown crate, with matches highlighted.
- The footer back to `+`, `≡`, gear and time.
- No change to what a filter does to play order, previews or counts; the list still updates within 16 ms for 5,000 entries.

**Non-Goals:**
- Searching across all crates, or Discogs/Bandcamp from the bar.
- Field prefixes (`label:`, `cat:`), regular expressions, fuzzy matching.
- Remembering the search across crates or restarts.
- Offering the artist, label or style filters in crates that don't offer them today.
- A way to hide the bar.

## Decisions

### The bar is chrome, not a list row
It is a stretchable bar `pl_filter_{l,fill,r}` drawn under `pl_top_*` with `draw_stretched_bar`, using the same `bar_piece` gradient and bevel as the footer, plus a stretchable sunken box `pl_field_{l,fill,r}` for the search field. The bar's contents are laid out at runtime (no layout entries), and the unused `pl_bpm` entry is gone. `SkinDef` gains `pl_filter_h` (serde default, 16), and `layout.rs` adds it wherever it adds `pl_top_h + pl_bottom_h`; the list starts at `pl_top_h + pl_filter_h`. The window grows by the bar's height and the list keeps its rows.
*Alternatives:* taking the list's first row (the list shrinks and jumps if the bar ever hides; it looks like a row, not part of the player); putting the field in the title bar (no room next to the crate name at 275 px).

### Always shown
The bar is drawn in every crate, even one with nothing to filter, where the search field fills it. A bar that appears and disappears moves the list when switching crates.
*Alternative:* a fold toggle. Not needed now; it can come later if 275 px users miss the strip.

### Search matches folded text, with `skin::fold`
A query is split on whitespace into words; each word and each searchable field are folded with `skin::fold` (upper case, accents stripped, char for char). An entry matches when every word appears in at least one of: artist, title, `album()` (record title), the record's artist, label, catalogue number. Reusing `fold` means the field draws in the skin font exactly what is matched, needs no dependency, and keeps char positions so highlighting can map a match back to the drawn glyphs.
*Alternatives:* `unicode-normalization` (a dependency for what `fold` already does for the accents that occur in record names); lowercasing only ("Âme" wouldn't match "ame").

### Search is one more field of `Shown`, not a filter of its own kind
`Playlist` gets a transient `search: Vec<String>` (folded words) that `Shown` borrows. `shows()` adds `&& words.all(...)`; `is_filtered()` counts it. So the play order, previews, `k/N`, P and record rows follow the search with no new code. It is not part of `SavedPlaylist`, and the app clears it when the shown crate changes. P on a hidden playing entry and × clear it with the filters; Esc clears only it.
Matching folds chars on the fly, without allocating, and meets 16 ms for 5,000 entries in release with room to spare, so no folded-text cache was needed.

### The field is a skin-font display over an invisible `TextEdit`
An egui `TextEdit` (frameless, transparent text) inside the inset box owns focus, caret, selection, IME and clipboard; the app paints the folded text and the caret in the skin font on top. Because `handle_keys` already yields to a focused text field, typing never triggers the letter shortcuts. Enter plays the first shown entry, ↓ moves focus to the list cursor, Esc clears and leaves the field. Cmd+F (egui's `command` modifier, so Ctrl+F off macOS) focuses it.
*Alternative:* a visible egui `TextEdit` (like the facet lists use): shows every character, but looks foreign on the skinned strip.

### Highlighting colours runs of the row text
Rows are drawn with egui's proportional font, not the skin font. `search_marks` finds the chars each word covers (folding keeps one char per char), and `text_marked` draws the row as a `LayoutJob` whose matched runs are in `pl_current`. Entry rows, column cells and record row names use it. On the playing row, already drawn in `pl_current`, the highlight doesn't show.

### Width tiers move up unchanged, plus FILTERS
The bar lays out, left to right: the search field (it takes the space left over, at least 60 px), the BPM control, then the filter controls in today's tiers (chips + buttons; else STYLES/ARTISTS/LABELS/FORMATS buttons; else) — the third tier, "nothing", becomes one FILTERS button showing the number of set filters — then CART when it fits (it goes in the panel otherwise), then × while anything is set. The search field's width is what the controls want subtracted from the bar (never under 60 px), and ×'s place is kept even while it is hidden, so nothing moves under a dragged BPM handle when the first range is set. A crate with no filter but a CART switch that doesn't fit still gets FILTERS. The tier code moves from the footer to the bar; the "clear of the time readout" constraint disappears.

### One panel with tabs replaces the per-facet popups
The style, artist, label and format lists already share a shape (count-sorted values, search field, checkboxes, Clear). They become tabs of one popup (STYLE · ARTIST · LABEL · FORMAT, only the offered ones, plus a CART switch in seller crates with a cart). Each bar button opens it on its tab; FILTERS opens it on the first tab with a set filter, or the first tab.

### Entry right-click picks a value, or searches it
"Only this artist / label / style" call the existing pick code for that facet, so the button lights and the panel shows why the list shrank. Where those facets aren't offered (dig, label and seller crates), the menu offers "Search ‹label›" and "Search ‹catno›" (when present), which set the search text and focus the field.

## Risks / Trade-offs

- [The window gets ~16 px taller at every size] → It is the cost of one always-visible place for filters; the footer gets lighter. Revisit with a fold toggle only if users ask.
- [Characters outside the skin font (ø, ß, CJK) don't draw in the field] → They still match (fold keeps unknown chars); the field shows the rest. Same limit the title line already has.
- [`fold` only uppercases ASCII] → "ø" doesn't match "Ø". Acceptable: rare in record names, and the same rule the display uses.
- [Typing re-filters 5,000 entries every keystroke] → cached folded haystacks; the existing 16 ms test is extended to the search.
- [Moving controls breaks pixel-based headless tests] → First task: one `LIST_TOP` constant for the 12 hard-coded offsets, run the suite green with an empty bar, then move controls.
- [Removing ☰ items removes muscle memory and the keyboard-free path at 275 px] → FILTERS is always in the bar at every width, and Cmd+F reaches the bar from the keyboard.

## Migration Plan

Saved per-crate filters (BPM range, picks, cart switch) keep their format and meaning; only their controls move. No settings migration. Rollback is reverting the change; the saved state stays readable.

## Open Questions

None blocking. The bar height (16 px) and the search field's minimum width are tuned during implementation against the 275 px layout.
